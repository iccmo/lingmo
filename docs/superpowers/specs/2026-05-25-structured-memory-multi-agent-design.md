# 灵墨 · 结构化记忆 + 多 Agent 协作架构设计

> 2026-05-25 · 架构讨论

---

## 一、问题

### 1.1 市面 AI 写小说的通病

- **50 章后必崩**：前文设定被遗忘，角色行为前后矛盾
- **Agent 分工无效**：分成「写手」「编辑」「策划」，但指令泛化，和一人干没区别
- **质检不精准**：打分 0.8 → 不知道哪里 0.8、怎么改 → 只能重写碰运气
- **没有记忆**：角色第 3 章的性格和第 30 章不是同一个人
- **没有伏笔**：第 5 章埋的钩子，没人记得要在第 25 章收

### 1.2 根因诊断

不是「AI 不够聪明」，是**记忆架构错误**。

当前所有方案都是：「把最近 N 章文本塞进 prompt → AI 生成」。
这是**概率模型当数据库用**，注定在 50 章后崩溃。

---

## 二、核心洞察：数据库写小说，AI 只是笔

人类作家写到第 50 章，不会重读前 49 章。他查的是：

- 林尘现在什么情绪？身上有什么伤？知道了什么？
- 还有哪些伏笔没收？
- 上次在青云山发生了什么？

答案不是靠「回想」，是靠**查询**。

## 三、结构化记忆系统

### 3.1 数据模型

生成第 51 章前，不是塞 50 章文本，而是：

```sql
-- 查询当前状态，不是回想去年的文本
SELECT * FROM character_state WHERE chapter = 50;
SELECT * FROM foreshadowing WHERE resolved = 0 AND due_by <= 55;
SELECT * FROM location_history WHERE name = '青云山' ORDER BY chapter DESC LIMIT 3;
```

返回的是**结构化事实**，不是模糊记忆。

### 3.2 表结构

```
story_bible（故事圣经）
├── character_state          — 角色状态表（每章更新）
│   ├── novel_id
│   ├── chapter_num
│   ├── char_name
│   ├── emotion               — 当前情绪
│   ├── physical_state        — 身体状态（受伤/健康/...）
│   ├── knowledge             — 已知信息（JSON array）
│   ├── goal                  — 当前目标
│   ├── location              — 当前位置
│   ├── relationships         — 对其他人物的态度变化（JSON）
│   └── updated_at
│
├── foreshadowing             — 伏笔契约表
│   ├── id
│   ├── novel_id
│   ├── created_chapter        — 埋下伏笔的章节
│   ├── description           — 伏笔描述
│   ├── hint_text             — 原文中的暗示片段
│   ├── due_by_chapter         — 预期回收章节
│   ├── resolved              — 是否已回收
│   ├── resolved_chapter       — 实际回收章节
│   ├── resolved_text          — 回收文本
│   ├── status                — active / overdue / resolved
│   └── created_at
│
├── location_history          — 地点历史表
│   ├── novel_id
│   ├── chapter_num
│   ├── location_name
│   ├── event                 — 在此处发生的事件
│   ├── state_change          — 地点状态变化（被毁/重建/...）
│   └── created_at
│
├── timeline                  — 时间线表
│   ├── novel_id
│   ├── chapter_num
│   ├── absolute_time          — 故事内时间（如"第37天"）
│   ├── relative_time          — 相对上一章的时间差
│   ├── event_summary
│   └── created_at
│
├── world_state               — 世界观状态表
│   ├── novel_id
│   ├── chapter_num
│   ├── rule                   — 规则名称
│   ├── rule_description
│   ├── is_broken              — 是否在本章被破坏
│   └── created_at
│
└── consistency_log           — 一致性校验日志
    ├── novel_id
    ├── chapter_num
    ├── check_type             — character / foreshadowing / world / timeline
    ├── severity               — error / warning
    ├── description            — 问题描述
    ├── fix_suggestion
    ├── was_fixed              — 是否已修复
    └── created_at
```

### 3.3 自动提取流水线

每章写完 → LLM 解析 → 结构入库：

```
第51章原文
  ↓
LLM 提取 Prompt：
"从以下小说章节中提取：
1. 每个角色在本章的：情绪变化、身体状态变化、新获得的知识、目标变化、位置变化
2. 本章埋下的新伏笔（描述+原文暗示+应该在几章内回收）
3. 本章新出现或状态变化的地点
4. 本章发生的时间（绝对+相对）
5. 是否打破或改变任何世界观规则
输出 JSON 格式。"
  ↓
自动入库 → story_bible 更新
```

## 四、编辑室 Agent 架构

### 4.1 角色定义

| Agent | 职责 | 输入 | 输出 |
|-------|------|------|------|
| **总编** | 全局决策：定调·节奏·删改 | 上一章 + story_bible | 本章简报（500字） |
| **结构师** | 本章大纲设计 | 简报 + story_bible | 3-5 情节点 + 角色分配 |
| **写手** | 正文初稿 | 大纲 + story_bible | 完整正文 |
| **事实核查** | 一致性校验 | 正文 + story_bible | 矛盾清单 |
| **伏笔总监** | 伏笔管理 | 正文 + foreshadowing 表 | 该收未收/该埋未埋 |
| **编辑** | 精确修改意见 | 正文 + 核查结果 | 具体到行号的修改指令 |
| **风格编辑** | 去 AI 味 + 润色 | 修改后正文 | 最终稿 |
| **总编（复核）** | 最终审核 + 更新圣经 | 终稿 + 所有校验结果 | 更新后的 story_bible |

### 4.2 工作流

```
1. 总编 读"上一章终稿 + 当前 story_bible"
   → 写「本章简报」（不写正文，只写要求）
   例："本章需要：(1) 林尘在青云山发现师叔的秘密实验室
        (2) 和秦默有一次冲突——秦默反对他独自行动
        (3) 结尾揭示师叔认识林尘的父母
        (4) 回收伏笔 #3（师叔可疑）
        (5) 林尘的左臂伤还没好，不能大动作战斗"

2. 结构师 根据简报 → 出本章大纲
   例：[
     {type:"开场",description:"林尘潜入实验室，发现古镜碎片",characters:["林尘"],location:"青云山·地下"},
     {type:"冲突",description:"秦默追来，两人争执",characters:["林尘","秦默"],location:"实验室门口"},
     {type:"发现",description:"发现师叔留下的书信，提到林尘父母",characters:["林尘"],location:"实验室内"},
     {type:"结尾",description:"师叔声音从暗处传来——'你终于来了'",characters:["林尘","师叔(声)"],location:"实验室"}
   ]

3. 写手 根据大纲 + story_bible → 写初稿

4. 事实核查 对照 story_bible 逐项检查：
   "第247行：林尘用右手持剑格挡 → 但 story_bible 记录他左臂伤 → ✅ 合理（用的右手）"
   "第312行：秦默说'你父母是被玄天宗害死的' → story_bible 记录秦默不知道这个信息 → 🔴 错误"
   → 输出矛盾清单

5. 伏笔总监 对照 foreshadowing 表：
   "伏笔 #3 状态 active，本章涉及师叔可疑行为 → ✅ 已回收"
   "伏笔 #7 须在第20章前回收，现在是第51章 → 🔴 过期未收，紧急"
   → 输出伏笔报告

6. 编辑 综合核查结果 + 伏笔报告 → 出精确修改意见：
   "第312行：秦默不能说'玄天宗'，她此时只知道'那个组织'。改为：'你父母是被那个组织害死的'"
   "第450行：缺少伏笔 #4 的暗示（秦默的疤痕）。在秦默出场时加一句她下意识摸手腕。"
   → 注意：不是打分，是指出具体行号和修改方向

7. 写手 根据编辑的修改意见定向修改 → 只改问题行，不重写

8. 风格编辑 统一润色 → 去 AI 味 → 完稿

9. 总编 复核 → 更新 story_bible → 准备下章简报
```

### 4.3 与市面 Agent 框架的本质区别

| | 市面 Agent | 灵墨编辑室 |
|---|---|---|
| 角色分工 | 按功能分（写/改/审） | **按职责分，每人管一件事，产出可验证** |
| 给写手的指令 | "写第5章" | **"本章需要：① 线索X ② 冲突Y ③ 收伏笔#3 ④ 林尘左手不能用"** |
| 质检方式 | 打分 0.8 | **"第312行角色冲突，秦默不应知道X → 改为Y"**  |
| 记忆系统 | 最近5章文本 | **story_bible：结构化实时查询** |
| 重写策略 | 重新生成 | **编辑给定位反馈 → 写手定点修改** |
| 一致性 | 50章后崩溃 | **每章自动校验 → consistency_log → 强制修正** |

## 五、一致性自动校验

### 5.1 校验规则

每章写完，自动运行：

```
1. 角色一致性
   - 每个出场角色的情绪/知识/身体状态是否与 story_bible 一致
   - 角色是否使用了不该有的能力（受伤/失去）
   - 角色是否知道了还未揭示的信息

2. 伏笔一致性
   - 该收的伏笔收了没有
   - 过期未收的伏笔标记 overdue → 总编强制下章回收

3. 世界观一致性  
   - 是否违反已建立的世界规则
   - 力量体系是否被打破（突然变强无解释）

4. 时间一致性
   - 时间线是否合理（不可能一天内跨越三个城市）
   - 角色年龄是否一致

5. 道具/物品一致性
   - 物品是否凭空出现或消失
   - 已被摧毁的物品是否又被使用
```

### 5.2 严重级别

- 🔴 **error**：强制修正，不修正不能发布
- 🟡 **warning**：提醒总编注意，可选择性修正
- 🔵 **info**：建议性优化

## 八、AI 文本的「恐怖谷」

### 9.1 问题

```
人类写："她站在门口，没进来。我看着她，她看着地板。"
AI 写："她站在门口，迟迟没有进来。我注视着她，她则低头看着地板，似乎有些犹豫。"
```

AI 把所有空白填满了——"似乎有些犹豫"剥夺了读者自己感受的权利。AI 不知道"少即是多"，因为"空"不是 token。

### 9.2 解法：反向润色（克制编辑）

专门做一个 Edit Pass，**只删不加**：

```
编辑 Agent 的反向 Prompt：
"以下是小说文字。你的任务：
1. 删掉所有读者自己能感受到的描写（不要解释情绪，让动作和对话自己说话）
2. 删掉所有过度词（突然、竟然、似乎、有些、其实）
3. 删掉所有重复信息（上一段暗示过的，下一段不说明）
4. 如果删完字数不足，简短不是缺点"
```

## 九、ICEBERG：「不说出来的那 7/8」

海明威：「如果作家足够了解自己写的东西，他可以省略。读者会感觉到那些省略的东西。」

### 10.1 子文本数据库 —— 人类维护的「不说之书」

```
unsaid_book（每章人类补充）：
├── 林尘知道他父亲还活着，但不能告诉任何人。
│   → 当别人提到"父亲"，他沉默不是在悲伤，是在忍耐。
│   → 不在正文里。但 AI 按"他在忍耐"写表面反应。
│
├── 秦默暗恋林尘，永远不会承认。
│   → 她的每一句"我是为了大局"都在撒谎。AI 按"撒谎"写。
│
├── 这个世界的神不存在，神迹是伪造的。
│   → 正文里人物都信神。唯一怀疑的角色——他的怀疑是"异端"。
│   → 读者到第 30 章才能开始怀疑。
```

AI 不是写真相，是写表面的真实。真相只在 unsaid_book 里。这就是冰山那 7/8。

## 十、主题引力场

### 11.1 主题不是 prompt，是约束——像引力场一样影响所有生成

不是：「请写关于母爱的故事」（太抽象）

而是：

```
【本章主题约束】
"在本章中，有一个角色做了牺牲。自愿的、不被注意的、不求回报的。
做牺牲的人自己不会说，旁边的人没看到。只有读者看到。
这是你的约束——每个句子都必须在这个约束下写。"
```

AI 在所有可能的方向中，只有一个被允许——而这个方向恰好产出母爱。**主题不是写出来的，是被约束逼出来的。**

## 十一、Voice Profile：学习人类的审美

### 12.1 人类标注 → Voice Profile 更新

```
每章人类标注 → Voice Profile 学习：
├── 喜欢的句式：短句 > 长句 / 对话 > 描写 / 冷峻 > 煽情
├── 不喜欢的模式：AI 味转折词、过度的心理描写
├── 角色声音：秦默 = 话少但每句都狠 / 林尘 = 内心戏多
└── 节奏偏好：动作 < 300 字 / 感情戏可长
```

### 12.2 不用 prompt，用 in-context examples

```
以下是这个角色之前的对白，请模仿：
[示例1] "她说她没哭。"秦默把烟掐灭。"我没问。" ← 人类认可的
[示例2] "你走吧。"她没抬头。门关上之后，她才把手里的东西放下来。 ← 人类修改过的
[示例3] "不用。" ← 一个字，人类最爱
```

比任何 prompt 都有效——AI 学的是具体选择，不是抽象指令。

## 十二、新手入门：系统帮 Ta 学会判断

### 13.1 不是给出好选择，是解析选择的后果

```
三个版本并排展示：
  A版 "A版信息密度高，适合推进剧情，但读者情绪参与感弱"
  B版 "B版调动读者情绪最强，但可能在 3 章后显得用力过猛"
  C版 "C版角色质感最好，但可能让读者产生距离感"
```

不是给结论，是给「选择会带来什么后果」。

### 13.2 最大的帮助：帮 Ta 建立「内在画面」

AI 在下笔之前先问问题，不先给答案：

```
"林尘进房间之前，在外面发生了什么？"
"他进来为了找什么？还是躲什么？"
"他此刻最怕房间里有谁？最希望有谁？"
"光线是什么颜色？为什么是这个颜色？"
```

4 个问题答完，脑子里有画面了。这时候写「林尘走进房间」，就是自己的句子了。

## 十四、关键设计决策

1. **不是 Agent 写小说，是数据库写小说，AI 只是笔**
2. **每个 Agent 只做一件事，产出可验证**
3. **编辑不是打分，是给出具体行号的修改指令**
4. **一致性不是靠 prompt 约束，是靠自动校验 + 强制修正**
5. **审美不是靠规则，是靠人类做选择、AI 做产能**
6. **冰山法则：最重要的信息不在正文里，在 unsaid_book 里**
7. **主题不是写出来的，是被约束逼出来的**
8. **AI 的终极价值：不是替代创作，是帮人建立创作所必需的「内在画面」**
