## 一个事实

灵墨的竞争力只有一个：**AI 写出来的东西能直接用**。

不是架构漂亮，不是部署方便，不是社区活跃。是质量控制。

竞品在架构、记忆、部署上领先我们。但没有一个在"写出来的小说质量"上超过我们。这是我们的基因，也是唯一的护城河。

所以优化方向不是补齐短板——是把自己的长处拉到更长。

## 优先级重排

### P0：用户现在就用不了的东西（本周必须修）

| # | 问题 | 证据 | 方案 |
|---|------|------|------|
| 1 | **服务器不稳定** | 本轮对话中后端挂了至少 5 次 | 加进程守护（systemd/launchd），或至少启动脚本加自动重启 |
| 2 | **引号修复不生效** | Flash 批量生成章节曾出现 70-132 个孤儿引号；`de_ai` 单独测试能修，但批量 DB 落库仍保存脏正文 | 已修：批量保存前 final `de_ai`，DB 使用同一份 `save_body`，残留孤儿引号直接拒绝落库；回归测试覆盖 |
| 3 | **FreeLLM token 过期** | 之前测试返回 492 错误，用户配置了也无法用 | 加 token 过期检测 + 友好提示 |

### P1：直接影响用户留存的东西（本月）

| # | 内容 | 为什么重要 | 怎么做 |

## 明确不做的

| 项目 | 原因 |
|------|------|
| **Agent Loop（LLM 自主决策）** | 风险高（成本翻倍、可能不终止）、用户未要求。novel-ai 做这个是因为它们的生成管线本身弱，需要 Agent 补偿。我们的固定管线已经够好 |
| **3 层记忆完整版** | 每章额外 2+ 次 LLM 调用，成本翻倍。用户感知的提升不明确。1 层轻量版够用 |
| **知识市场** | 需要服务器 + 审核 + 用户系统，solo dev 不现实 |
| **多用户/OIDC** | 保持单用户本地工具定位，不要膨胀 |

## 为什么不是"追竞品"

novel-ai 做 3 层记忆 + Agent Loop 是因为他们的生成管线本身弱——一个简单 prompt 直出文本，没有质量评分、没有重试、没有自动校准。他们用架构复杂性补偿生成质量的不足。

我们的 12 步管线、8 维评审、排版修复、作家声音、自动校准——这套东西跑出来的小说质量已经很高。在这个基础上再加 Agent Loop，边际收益很低。

webnovel-writer 4.7k stars 是因为先发优势 + Claude Code 生态。我们是独立 Web 应用，不是同一个赛道。

**我们的路线是：质量控制做到极致 → 降低使用成本 → 扩大覆盖面。不是：追架构 → 追生态 → 追社区。**
